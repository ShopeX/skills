# 自然语言购物状态机

## 目标

在尽量减少非必要提问的前提下，将自然语言购买意图推进至订单详情和支付二维码，同时保留不可省略的订单与支付安全确认。

## 意图槽位

首次解析用户原话，维护以下状态：

| 槽位 | 示例 | 阻断条件 |
|---|---|---|
| product | 「绿野寻踪徒步鞋」 | 无可靠候选或多个同名候选 |
| variant | 「42 码、黑色」 | 商品有多个 SKU 且无法唯一确定 |
| quantity | 「两双」 | 未提供时默认为 1，并在确认摘要中展示 |
| address | 「常用地址」 | 多地址且无默认地址 |
| coupon | 「能领的都领掉」 | 不阻断商品核验；结算前完成 |
| target | 「下单并给我二维码」 | 决定流程终点 |

禁止询问非阻断信息。数量未给出时可默认 1；规格只有一个可售选项时直接选择并在摘要中展示。

## 状态机

### S0：解析意图

1. 提取商品、规格、数量、地址、优惠和目标。
2. 判断用户是否已经表达订单创建和二维码生成意图。
3. 禁止将「帮我买」直接视为最终订单提交确认；它表示进入购买流程。

### S1：匿名发现

1. 搜索候选并核验名称。
2. 仅将匿名查询结果作为候选，不得将匿名上下文中的 `company_id` 作为最终商城上下文。
3. 候选唯一且可靠时继续；否则展示关键差异并让用户选择。

### S2：会员授权

1. 查询授权状态。
2. 优先使用浏览器 OAuth，让用户仅在可信授权页中输入凭据。
3. 若当前部署明确不支持 OAuth，使用连接器提供的安全凭据输入界面；普通对话不得收集密码。部署差异见 [pitfalls.md](pitfalls.md) 第 2 条。
4. 禁止在对话中复述任何授权值，也不得硬编码演示环境的 `company_id` 或账号。

### S3：会员店铺复核

1. 从会员业务响应识别实际 `company_id`。
2. 在该商城重新搜索目标商品。
3. 重新核验 SKU、价格、库存、销量和商品状态。
4. 若商品不属于会员商城，停止并告知匿名候选不可直接下单。

### S4：优惠优化

1. 查询公开券与会员券。
2. 用户要求「全部领取」时，领取所有当前可领取且无额外付费的券。
3. 每次领取后重新查询会员优惠券，验证领取结果。
4. 计算多个可用方案；最终以结算预览返回的实际抵扣金额为准。
5. 禁止使用历史持券记录证明本次领取成功。

### S5：地址解析

按顺序选择：

1. 用户明确指定的地址。
2. `is_def == 1` 的默认地址。
3. 仅有一条地址时使用唯一地址。
4. 多条且无默认地址时展示脱敏选项让用户选择。
5. 无地址时收集完整字段，保存后重新查询稳定 `address_id`。

### S6：准备结算

1. **加购（cart 模式）**；本后端 `fastbuy` 路径未对接，禁止使用（见 [pitfalls.md](pitfalls.md) 第 3 条）。
2. 写入后回读购物车，获取目标 `cart_id`。
3. `cart_select` **逐条**勾选：目标行 `is_selected=true`，其余 `false`（批量 `cart_ids` 会被 422 拒绝）。
4. 再次回读，验证目标商品、数量、单价和勾选状态。
5. 状态未变化时停止，禁止仅依据成功摘要继续。

### S7：结算预览

1. 使用稳定地址与本次商品参数预览。
2. 读取商品金额、优惠、运费、积分抵扣和应付金额。
3. 验证本次结算明细只包含目标商品。
4. 若价格、库存或优惠变化，返回 S4/S6 并重新确认。

### S8：订单确认

用一次摘要展示：

- 商品、规格、数量。
- 脱敏收货信息。
- 优惠与运费。
- 应付金额。
- 支付方式。

用户此前说「确认下单」可满足业务确认，但必须先完成订单 dry-run。`guard.confirm_token` 对 agent 不可见（被脱敏），提交时使用 **`confirm=true`** 连同原参数调用，禁止复用旧 token（见 [pitfalls.md](pitfalls.md) 第 8 条）。

### S9：创建订单

1. dry-run 获取确认态（禁止试图复制不可见的 token）。
2. 用户确认后用**完全相同参数 + `confirm=true`** 提交；必须带 `distributor_id`（来自预览）与显式 `coupon_code`。
3. 检查业务字段，必须获得有效 `order_id`。
4. 缺少订单号、包含业务错误或金额不一致时停止。
5. 订单创建会移除对应购物车行，取消订单不会恢复该行；再次创建订单前，必须先调用 `cart_item_add` 获取新的 `cart_id`（见 [pitfalls.md](pitfalls.md) 第 6 条）。

### S10：生成支付二维码

1. 确认订单仍属于当前会员且可支付。
2. dry-run 获取确认态；提交使用 `confirm=true`（token 不可见，禁止复制）。
3. 用户已明确要求在订单创建后提供二维码时，不再重复询问该偏好；直接完成工具规定的确认步骤。
4. 从商城后端获取 `code_url`；当前部署未接入微信支付时可能返回「系统繁忙」，必须分别说明订单创建、二维码生成、支付发起和支付结果状态（见 [pitfalls.md](pitfalls.md) 第 9 条）。
5. 将其原样编码为二维码，禁止改写、禁止打开、禁止附加参数。

### S11：交付

在同一视图中展示二维码与订单详情。状态分三层表达：

1. 订单创建成功。
2. 支付二维码生成成功或失败。
3. 支付成功、未支付或待确认。

禁止将前两层成功合并表述为「支付成功」。

### S12：支付结果核验与状态自动更新

1. 支付二维码生成时可能返回「系统繁忙」。该响应不能单独证明支付最终失败；用户扫码后的支付结果仍可能由后续支付通知更新。
2. 订单后端状态变更完全由后台驱动：微信支付结果通知（回调）到达商城 → 商城核对交易流水 → 自动将 `order_status` 从 `NOTPAY` 更新为 `PAYED`。**没有任何工具可手动改写订单状态**（连接器刻意不暴露，防伪造支付）。
3. 核验支付结果使用两个只读工具，按 ID 查询：
   - `ecshopx_member_order_detail({order_id})` → `order_status` / `pay_status`（`PAYED` 即已支付）、`order_status_msg`（待发货）。
   - `ecshopx_member_trade_detail({trade_id})` → `tradeState`（`SUCCESS` 即支付成功）、`transactionId`、`payDate`。
4. `ecshopx_member_orders_list` 默认可能不返回已支付分组，因此禁止将其结果用于判断订单是否存在；必须按 `order_id` 和 `trade_id` 查询详情。
5. 仅当 `order_detail` 显示 `PAYED` 且 `trade_detail` 显示 `SUCCESS` 时，才可在交付视图中将状态更新为「已支付·待发货」，并附上交易流水号与支付时间。

## 最少追问规则

仅在以下情况提问：

- 可靠商品候选不唯一。
- SKU/规格无法唯一确定。
- 数量含糊且不能安全默认。
- 多地址且无默认地址。
- 价格、运费或优惠发生变化。
- 创建订单所需明确确认尚未获得。
- 用户要求与商城能力冲突。

以下情况禁止提问：

- 唯一可售规格。
- 数量缺失且可默认 1。
- 用户已说「常用地址」且存在唯一默认地址。
- 用户已说「能领的券都领掉」。
- 用户已说「下单后给我支付二维码」。
